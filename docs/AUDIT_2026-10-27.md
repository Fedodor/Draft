## 2. Executive summary

The architecture is sound and the GSI -> engine -> overlay path works end-to-end. The dominant risks are:

1. The recommendation path is expensive, uncoalesced, and duplicated across two windows.
2. The ML term consumes 25% of the score while the shipped model is statistically near a constant baseline, and it was trained on complete drafts but queried on partial drafts.
3. Draft-session lifecycle and Captain's Mode fallback can silently produce wrong state.
4. Several user-facing settings are inert, and optional ML failures can blank the primary overlay feature.

| Area | Grade | Verdict |
| --- | --- | --- |
| Architecture / module boundaries | B+ | Clean separation; engine is a god-object with lock coupling |
| Backend correctness | C+ | Happy path works; lifecycle and validation gaps |
| Performance | D | ~126 serialized ONNX inferences per request inside the global engine lock (analytical) |
| ML quality | D | Test ROC-AUC 0.5388 / Brier 0.2481 vs 0.25 constant baseline, yet 25% weight |
| Frontend correctness | C | No debounce/versioning; overlay can blank out |
| Security | C- | `csp: null`, broad overlay capabilities, arbitrary model path |
| Data / MLOps | D+ | 1.9 GB / 121,746 loose dataset files; no registry or retention |
| Test coverage | C- | Good unit coverage; zero lifecycle/concurrency/perf tests |
| Documentation | B- | Strong but conflicts on feature counts, AUC, and lane status |

## 4. P0 findings

### P0-1. ML contributes 25% of the score with near-baseline accuracy

- Evidence at audit time: `apps/desktop/src-tauri/src/engine/scorer.rs:44` (`W_ML = 0.25`), applied at `engine.rs:525` and `engine.rs:912`.
- Bundled manifest `ml/models/draft_model_xgboost_full_manifest.json`: 887 features, test ROC-AUC **0.5388**, Brier **0.2481**, accuracy **0.5294**. A constant 0.5 predictor scores Brier 0.25.
- Training used complete 5v5 drafts (`ml/training/train_full.py`); inference queries partial drafts (1-10 actions).
- The UI emits "ML model favors this pick" explanations from this term (`engine.rs:579-589`).

Impact: the ML term can displace genuinely informative matchup/synergy signals and the UI overstates its reliability. Early-pick recommendations are the least reliable and the most visible.

Status: **confirmed** by code + artifact inspection.

### P0-2. Draft lifecycle corruption in GSI ingestion

- `gsi.rs:350` `process_draft_update` appends picks with `add_pick` and no validation.
- Dedupe key is `(hero_id, team, order)` (`gsi.rs:358-383`), so the same hero can be added twice when the slot order differs, and a picked hero can also be banned.
- No reset on match start/end; `available_heroes` is never restored (`gsi.rs:350-410`).
- Manual undo is re-added by the next GSI payload because ingestion only appends.

Impact: second game in a session can start with stale picks; duplicates pollute scoring and the hero pool.

Status: **confirmed** by code inspection.

#### P0-2 remediation (2026-10-27, session 2)

Status: **`verified_fixed`** at the payload -> engine level. Live Dota 2 GSI replay and the warp/Tauri emission layer were **not** exercised and stay outstanding.

What changed:

- `apply_gsi_payload` was extracted from `handle_gsi_update` (same module). It owns auth -> parse -> new-draft detection -> reconcile and is free of `tauri::AppHandle`, so tests drive the exact function the warp handler calls. `handle_gsi_update` now only maps the outcome to an HTTP status and emits `gsi-team` / `gsi-update`. No public interface changed.
- `reconcile_draft` now enforces `MAX_BANS_PER_TEAM = 5`. Before this, picks were capped at 5 per side by `validate_pick`, but bans were unbounded: renumbered or stale snapshots could append a sixth ban to a side, permanently removing that hero from `available_heroes`. The property test found this (`more than 10 bans`), the guard fixed it, and `lifecycle_bans_are_capped_per_team` pins it. Five is derived from the five `banN_id` slots and the audited CM order, not from a guess about slot timing.
- The ingestion core still skips exactly one payload when a new draft is detected. This is unchanged and documented below as a residual ambiguity.

New tests (`apps/desktop/src-tauri/src/gsi/lifecycle_tests.rs`, 18 tests):

| Area | Tests | What is asserted |
| --- | --- | --- |
| Consecutive matches (A) | `lifecycle_consecutive_matches_do_not_leak_state`, `lifecycle_strategy_time_after_draft_keeps_state` | init -> hero selection -> actions -> post-game/in-game -> second hero selection. The reset payload is skipped, no match-1 hero or ban survives, the pool is restored, match-2 actions are accepted, team/turn state is rebuilt, replay is a no-op, strategy/pre-game do not reset. |
| Duplicate/invalid (B) | `lifecycle_duplicate_and_conflicting_actions_are_deduped`, `lifecycle_unknown_heroes_are_ignored_without_dropping_valid_actions`, `lifecycle_stale_snapshots_never_remove_or_duplicate_actions`, `lifecycle_malformed_payloads_are_rejected_without_mutating_state`, `lifecycle_auth_is_enforced_before_any_state_change` | same hero twice, hero in pick and ban (pick wins), unknown ids (including 0), older snapshot after a newer one, invalid JSON/shape, auth rejected before the lifecycle tracker advances. |
| Manual undo (C) | `lifecycle_manual_undo_is_not_reverted_by_repeated_snapshots`, `lifecycle_undo_suppression_clears_on_the_next_match`, `lifecycle_explicit_manual_pick_lifts_undo_suppression` | undone pick stays gone across repeated snapshots, a new action is still accepted, suppression survives post-game but not the next reset, explicit manual pick lifts it without double-counting a later snapshot. |
| Attribution/order (D) | `lifecycle_team_attribution_survives_repeated_snapshots`, `lifecycle_team_attribution_falls_back_to_slots`, `lifecycle_unrecognized_team_ids_fall_back_to_the_slot`, `lifecycle_duplicate_team_ids_cannot_overfill_a_side`, `lifecycle_bans_are_capped_per_team`, `lifecycle_cm_order_fallback_walks_the_full_draft`, `lifecycle_ambiguous_turn_payloads_are_handled_safely` | `team_id` beats slot, slot fallback, invalid ids fall back, duplicate ids cannot overfill, bans capped, all 20 CM actions drive `current_pick` correctly, `activeteam` without `pick` falls back, missing `draft` is a no-op. |
| Invariants/property | `lifecycle_invariants_hold_for_adversarial_payload_sequences` (+ `assert_invariants` used by every test) | 300 deterministic pseudo-random payloads: no hero picked and banned, no duplicate hero, all accepted heroes in the DB, `available_heroes` == pool minus accepted, <=5 picks and <=5 bans per side, `pick_number` consistent, replay idempotent, no panic. |

Remaining gaps / documented ambiguities:

- **No live GSI stream.** The fixtures are hand-written from the documented payload shape; no captured traffic or in-game session was replayed. A payload-shape surprise in the real client is still unverified.
- **warp + Tauri emission not covered.** The tests stop before the HTTP status and the `gsi-team` / `gsi-update` events. `apply_gsi_payload` is shared, but the handler's match arms are only type-checked.
- **Reset skips one payload.** The reset-triggering payload is deliberately not ingested because it can still contain the finished game's slots. A second stale `HERO_SELECTION` snapshot arriving after that (out-of-order delivery, which GSI does not promise against) is structurally indistinguishable from a new draft and would be accepted. No heuristic was added.
- **Undo suppression is hero-scoped for the match.** It cannot tell a stale re-add from a genuine later pick of the same hero in the same match; the latter is ignored until reset. An explicit manual pick lifts it. This is intentional and tested as the current contract.
- **Append-only by design.** Ingestion never removes an action based on a snapshot, so Dota-side corrections that are not user undos cannot be represented. In CM, actions are not reversible, so this is acceptable for now.


### P0-3. Incorrect Captain's Mode fallback sequence

- `gsi.rs:270-291` encodes 6 bans -> 6 picks -> 4 bans -> 4 picks (20 actions).
- Audited current sequence: 4 bans -> 4 picks -> 4 bans -> 4 picks -> 2 bans -> 2 picks.
- The fallback is used when GSI omits `activeteam`/`pick` (`gsi.rs:304-311`) and is the only ordering authority in that case.

Impact: silent turn/team inversion when the fallback is exercised.

Status: **confirmed** by code inspection and table comparison.

### P0-4. Expensive recommendation execution

- `ml.rs:122` serializes every inference behind a `Mutex`; `ml.rs:242` runs one inference per candidate.
- `ml.rs:447` `build_feature_map` allocates a fresh ~887-entry `HashMap` for each candidate.
- The engine scores every available hero while holding the state read guard (`engine.rs:540-611`).
- `App.tsx:79-83` and `OverlayWindow.tsx:49-52` each request recommendations per `gsi-update`, and the overlay also polls every 5 s (`OverlayWindow.tsx:68-70`).
- Analytical estimate: up to ~126 inferences + ~126 feature-map builds per request; ~252 per GSI event across both windows. **Not measured in this audit.**

Status: **confirmed structurally**; latency magnitude is an estimate pending benchmark (see ROADMAP P0-4).

## 5. P1 findings

### P1-1. No debounce, coalescing, cancellation, or stale-response protection

`App.tsx:79` fires `getDraftState` + `getRecommendations` on every event and applies responses unconditionally. GSI can emit several payloads per second. Stale responses can overwrite newer state.

Status: **confirmed**.

### P1-2. Overlay can blank out and ignores the player's side

`OverlayWindow.tsx:49-54` wraps recommendations and `predictDraftValue` in one `Promise.all`; a missing/failed model rejects both. The overlay also defaults to `radiant` and never listens to `gsi-team` (`OverlayWindow.tsx:23,61-76`).

Status: **confirmed**.

### P1-3. Overlay toggle steals focus

`Header.tsx:43` calls `setFocus()` after showing the overlay, pulling focus from Dota 2.

Status: **confirmed**.

### P1-4. User-facing settings with no runtime effect

`overlay_enabled`, `overlay_position`, `overlay_size`, `ml_enabled`, `auto_update_meta`, and `preferred_language` are editable or stored but not applied. `ml_enabled` is the most damaging: users cannot disable the weakest 25% of the score. `AppConfig` also carries dead fields, and the default model path is the stale `ml/models/draft_model.onnx` (`models.rs:579-581`).

Status: **confirmed**.

### P1-5. Feature pipeline cannot reproduce the shipped feature set

`ml/feature-engineering/processor.py`: `_load_hero_matchups` expects name-based `hero_a`/`hero_b` + `winrate`, while `process_all_pick_matches` writes numeric IDs + `hero_a_winrate`. `all_hero_ids = 1..139` is hard-coded while the manifest contains `rad_wr_hero_145`/`_155`. Lane features are commented out.

Impact: the matchup/roster feature block cannot be regenerated from current code; retraining produces a different contract than the shipped model.

Status: **confirmed** by code inspection; end-to-end regeneration not run.

### P1-6. Post-draft and ordinal features create train/serve skew

`ml/training/train_full.py` includes `duration`, `avg_mmr`, `game_mode`, `lobby_type`, and raw `rad_pick_i`/`dire_pick_i` as numeric ordinals. `duration` is post-draft and is replaced by a median at inference.

Status: **confirmed**; impact magnitude not measured.

## 6. P2 findings

- **Security:** `tauri.conf.json:44` sets `"csp": null`; `load_ml_model` accepts an arbitrary path (`commands.rs:380`), which can sideload an `onnxruntime.dll`; `capabilities/default.json` grants `shell:default`, `fs:default`, `dialog:default` to both `main` and `overlay`; GSI auth is optional by default.
- **Semantics:** `confidence` is literally the score (`engine.rs:665`); `lane_balance` is constant `0.5` (`engine.rs:807`); `simulation.rs:196` uses immediate value as confidence; risk levels are score thresholds; no role/position, ban, or phase-aware output.
- **Crash paths:** `partial_cmp().unwrap()` on f32 keys at `engine.rs:595`, `simulation.rs:96`, `simulation.rs:139`.
- **Locking / async:** several async commands lock `std::sync::Mutex` directly (`commands.rs:63,102,115,140,160,168,178,187`); `predict_draft_value` introduces a lock-order inversion risk; `DraftSimulator` clones the whole engine including data maps (`simulation.rs`).
- **Ops:** no log rotation (`lib.rs:23-63`); `info!` on every recommendation (`commands.rs:38`) and GSI update (`gsi.rs:241`); ONNX load is synchronous on startup/IPC.
- **Data:** `ml/datasets` = 121,746 files / 1.9 GB (1 tracked); `ml/models` = 115 files / 17.7 MB (4 tracked); no incremental cache, versioning, or retention.
- **Docs:** feature count/AUC/lane status conflict across `README.md`, `AUDIT.md`, and the manifest; `docs/RefactorML.md` is empty.
- **Unused surface:** `getDataHealth` exists but nothing surfaces it in the UI.

## 7. P3 findings

- Hero database lookups are linear scans inside the candidate loop (O(n^2) per request; low absolute cost at ~126 heroes).
- `SearchConfig` is unvalidated (local DoS via simulator).
- `overlay_size` has no backing behavior.
- Bundle resource paths use brittle `../../../ml/models/...` relatives.

## 8. What was already working

- Rust library tests and frontend unit tests pass at baseline (see ROADMAP baseline record).
- ONNX model loads and the Rust feature contract matches the bundled model (golden test).
- Matchup/synergy scorers are wired to loaded data.
- Settings persistence and GSI port/auth/auto-start are real.
- `gsi-team` is emitted from the backend and handled by the main window.

## 9. Caveats

- Findings come from static reading plus unit tests. The latency numbers in this document are analytic (candidate count x serialized inference) and were **not** profiled for the audit itself. A later benchmark in the remediation session produced measured values (release: 23.2 ms with ML on, 0.2 ms with ML off, 0.002 ms cache hit); see [`ROADMAP.md`](ROADMAP.md) §3. Those are harness numbers, not in-app p95.
- `verify.ps1` was run for the audit only as its individual steps; the full gate is the recommended re-check for the next session.
- Severity assumes a single-player desktop tool. P1-4/P1-6 would be P0 in a networked or multi-tenant setting.
- The 2026-10-27 report's exact prose is not stored elsewhere in the repository; this document reconstructs it from the originating session and the current code. Nothing was invented beyond the evidence listed.
- Findings were re-verified against the tree before remediation. Where implementation changed during this session, §3a records the new status instead of rewriting the original evidence.
