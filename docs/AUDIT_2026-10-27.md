## 2. Executive summary

The architecture is sound and the GSI -> engine -> overlay path works end-to-end. The dominant risks are:

1. The recommendation path is expensive, uncoalesced, and duplicated across two windows.
2. The ML term consumes 25% of the score while the shipped model is statistically near a constant baseline, and it was trained on complete drafts but queried on partial drafts.
3. Draft-session lifecycle and Captain's Mode fallback can silently produce wrong state.
4. Several user-facing settings are inert, and optional ML failures can blank the primary overlay feature.

| --- | --- | --- |
| Architecture / module boundaries | B+ | Clean separation; engine is a god-object with lock coupling |
| Backend correctness | C+ | Happy path works; lifecycle and validation gaps |

## 4. P0 findings

### P0-1. ML contributes 25% of the score with near-baseline accuracy

- Evidence at audit time: `apps/desktop/src-tauri/src/engine/scorer.rs:44` (`W_ML = 0.25`), applied at `engine.rs:525` and `engine.rs:912`.
- Bundled manifest `ml/models/draft_model_xgboost_full_manifest.json`: 887 features, test ROC-AUC **0.5388**, Brier **0.2481**, accuracy **0.5294**. A constant 0.5 predictor scores Brier 0.25.
- Training used complete 5v5 drafts (`ml/training/train_full.py`); inference queries partial drafts (1-10 actions).
- The UI emits "ML model favors this pick" explanations from this term (`engine.rs:579-589`).

Impact: the ML term can displace genuinely informative matchup/synergy signals and the UI overstates its reliability. Early-pick recommendations are the least reliable and the most visible.

Status: **confirmed** by code + artifact inspection.

#### P0-1 remediation (2026-10-27 → 2026-10-28)

Status: **`in_progress`**. The mitigation (ML off by default, inference skipped, weights renormalized) and the automatic promotion gate are `verified_fixed`; model quality is still **open**.

What changed on 2026-10-28:

- `ml/training/quality_gate.py` re-evaluates the bundle on the manifest's chronological holdout and validates the artifact contract first (manifest ↔ schema ↔ features order, fingerprint, ONNX input/output). Evaluation errors exit 2; threshold failures exit 1; only exit 0 permits `--promote-to`.
- The policy is applied to **`inference` mode** (runtime defaults for post-draft/match fields) by default, with `as_trained` kept for comparison against the manifest. Thresholds: ROC-AUC ≥ 0.60, Brier ≤ 0.235, ECE ≤ 0.10, ≥ 500 rows.
- Fresh measurements on the full 102,118-row dataset: as-trained AUC 0.5388 / Brier 0.2481; inference AUC **0.5122** / Brier **0.2495** / ECE 0.0241. Constant train-prior Brier is **0.2493**. Decision: failed (`policy.roc_auc`, `policy.brier_score`), `promotion_eligible=false`.
- Split integrity re-verified each run: sizes 81,694 / 10,211 / 10,213, zero `match_id` overlap, strict chronological boundaries.
- Manual runtime opt-in remains allowed; the gate blocks automatic promotion only. Lowering thresholds or editing the shipped schema was rejected as a way to make the gate pass.

Residual: the bundled model is not better than a constant predictor on this holdout. The next step is a retrained candidate without post-draft/ordinal fields (P1-6), not a policy change.

#### P0-1 remediation, addendum (2026-10-29, session 8)

Status: still **`in_progress`**; `verified_fixed` applies only to the mitigation and gate. Two of the three candidate causes have now been tested and excluded.

- **Feature encoding (P1-6):** corrected (session 6-7). Correct pick/ban encoding is worth ~+0.011 to +0.014 validation AUC (0.5340 → 0.5454-0.5498) and is now worth ~0.0015 Brier over the constant prior. Necessary, not sufficient.
- **Learner family:** tested this session and excluded. On the identical 871-feature set, frozen split, and runtime-faithful partial-draft frames, XGBoost 0.5479 ± 0.0004, regularised logistic regression 0.5454 (seed-invariant), `HistGradientBoosting` 0.5380 ± 0.0026 (population A, 10,212 validation rows). The duplicate-hero-excluded population ranks them identically. Paired bootstrap: logistic − XGBoost AUC −0.0026 (−0.0098 … +0.0042, not distinguishable) and Brier +0.0015 (+0.0006 … +0.0024, reliably worse); hist GBDT is reliably worse on AUC.
- **Where the two models differ is the finding that matters for the product.** At one known pick per side the linear model is +0.011 AUC ahead (0.5372 vs 0.5262) and stays ahead through three picks; XGBoost only leads at five (+0.003). Interaction capacity is bought where the draft is already decided, which is the least valuable place to have it.
- All three families fail the unchanged policy on validation (AUC 0.538-0.548 vs 0.60; Brier 0.2473-0.2488 vs 0.235). Nothing was promoted; `quality_gate.py` was not re-run, and the test partition was not read, so **no new test result exists**.
- ONNX parity is verified for the XGBoost candidate (2.98e-07) and the logistic candidate (2.47e-07) on full-draft and 0/1/3-pick frames, in a gitignored candidate directory. `hist_gbdt` cannot be converted by skl2onnx (`TreeEnsembleClassifier` op builder rejects it); recorded as a tooling limitation instead of changing the runtime contract.

Consequence for P0-1: the residual is no longer "retrain with better features or a better model". It is a **target-definition** question — a single binary full-match outcome may not be the quantity the product should predict. That is the next experiment, and the bundled artifact stays as it is until a candidate passes the unchanged gate on clean data.

#### P0-1 target study (2026-10-29, session 9)

Status: **`open`**, but the search space is now bounded. Research only: no model
fitted for selection, nothing promoted, test partition not read. Details in
[`ML_TRAINING.md`](ML_TRAINING.md) §3d.

- **The corpus is the right population after all** (90.3% Captains Mode; see
  P1-7). Product alignment is not the problem.
- **The early-draft numbers were optimistic by ~0.004 AUC.** The harness held all
  seven bans per side at every stage; the real CM order reveals three before the
  first pick. Rebuilding with only the bans that had happened: 0.5228 at zero picks
  (was 0.5271) and 0.5219 at one pick (was 0.5248), against a constant-prior Brier
  of 0.2498. At the top of the draft the model is level with a constant.
- **Resolution limit:** the validation partition resolves AUC to +/-0.0111. The
  remaining gap to the 0.60 floor is about five standard errors; more data of the
  same kind narrows the interval, not the point estimate.
- **Ranking is not identifiable here.** 0 of 101,400 two-a-side contexts occur 50
  times; 38 of 102,080 full drafts repeat at all. Any per-pick "+X% win" claim
  would be model extrapolation, not an estimated effect.
- **Pick-level contribution is unidentified** (one match label per ten picks), but
  hero-level rates are measurable at +/-1.7 pp with genuine between-hero variance
  (observed SD 2.29 pp vs 1.04 pp binomial noise, SNR 2.0) — observational, and
  `avg_mmr` is identically 0, so skill cannot be controlled.
- **Verdict:** win probability is exhausted as a headline metric (A); conditional
draft-stage prediction (B) is the only objective the corpus supports today; the
next experiment is an identifiable one — a next-pick **imitation** model scored by
top-1/top-3 accuracy on held-out drafts. No counterfactual claim, no promotion, no
threshold change.

#### P0-1 imitation study (2026-10-29, session 10)

Status: **`open`**, but the product question now has a measurable target. Research
only; test partition never parsed. Details in
[`ML_TRAINING.md`](ML_TRAINING.md) §3e.

- **Chronology is trustworthy.** Raw `order` is dense and unique in every eligible
  CM payload; 94% share one 24-action template; 60/60 sampled matches agree with
  the parquet's pick slots and label. 3,022 payloads with null `order` are
  excluded rather than repaired, along with 2,005 malformed, 1,557 out-of-roster,
  2,791 unsupported-mode and 705 non-STRATZ rows: 81,701 of 91,907 candidates
  remain, 10 decision states each.
- **The state predicts the observed next pick from pick 2 onward.** Top-1 0.0551 /
  top-3 0.1312 versus 0.0405 / 0.0959 for a stage/side frequency table; match-level
  bootstrap +0.0146 (+0.0128..+0.0165). Against the same model's own intercept
  (state removed) the gain is +0.0249.
- **It does not at the opening pick**: 0.0744 versus 0.0990 for frequency, and
  0.1003 for the model's intercept alone. Ban→pick substitution coefficients
  learned later in the draft mislead a state with no picks. Early-draft usefulness
  is still unproven.
- **Two capacity fixes were necessary before the comparison was fair**: a per-phase
  hero intercept (without it the model could not represent the baseline at all)
  and pooled removal effects (1,668 → 562 features; on a 4,000-match smoke run the
  phase-specific version scored 0.0509 at the opening pick).
- **Imitation is not value.** Nothing here supports a win-probability or
  counterfactual claim, and no threshold changed.

#### P0-1 phase-aware imitation study (2026-10-29, session 11)

Status: **`open`**, with the early-draft question now answered negatively. Research
only; test partition never parsed. Details in
[`ML_TRAINING.md`](ML_TRAINING.md) §3f.

- **No trained early-stage model beats the frequency table.** A pick-0-only model
  (280 features) scores 0.0575 top-1 against 0.0990, −0.0416 (−0.0492..−0.0339); a
  shared picks-0-1 model scores 0.0601 against 0.0840, −0.0239 (−0.0291..−0.0187);
  a pick-1-only model is the closest at 0.0629 vs 0.0689 and still does not clear
  zero (−0.0061, −0.0124..+0.0007). The pre-registered rule therefore selects the
  frequency fallback, not a wider search.
- **The early signal is the prior, not the ban state.** The model's intercept alone
  (all removal columns zeroed) is indistinguishable from the table at picks 0-1
  (+0.0012, −0.0018..+0.0041) and collapses later (0.0039 at picks 8-9). Ban
  knowledge tells you what a captain is avoiding, not what they take first.
- **The hybrid is the best configuration measured so far**: table at picks 0-1,
  pooled model from pick 2 → 0.0599 top-1 overall vs 0.0551 pooled and 0.0405
  table, with the pooled model's +0.0249 (picks 2-7) and +0.0223 (picks 8-9) gains
  intact. It is a routing change only; no model was added.
- **A tuning-holdout transfer failure is on record**: the pick-0 model scored 0.0994
  on the last 15% of training matches and 0.0575 on validation. The internal
  holdout is an optimistic proxy for the next time window, so early-stage "gains"
  measured on it should not be trusted without the frozen partition.
- **Imitation is not value**, and this result does not make it value: predicting
  observed picks says nothing about win rate or optimality. No threshold, schema,
  split or production default changed.

### P0-2. Draft lifecycle corruption in GSI ingestion

- `gsi.rs:350` `process_draft_update` appends picks with `add_pick` and no validation.
- Dedupe key is `(hero_id, team, order)` (`gsi.rs:358-383`), so the same hero can be added twice when the slot order differs, and a picked hero can also be banned.
- No reset on match start/end; `available_heroes` is never restored (`gsi.rs:350-410`).
- Manual undo is re-added by the next GSI payload because ingestion only appends.

Impact: second game in a session can start with stale picks; duplicates pollute scoring and the hero pool.

Status: **confirmed** by code inspection.

#### P0-2 remediation (2026-10-27, session 2)

Status: **`verified_fixed`** at the payload -> engine level. Live Dota 2 GSI replay and the warp/Tauri emission layer were **not** exercised and stay outstanding.

What changed:

- `apply_gsi_payload` was extracted from `handle_gsi_update` (same module). It owns auth -> parse -> new-draft detection -> reconcile and is free of `tauri::AppHandle`, so tests drive the exact function the warp handler calls. `handle_gsi_update` now only maps the outcome to an HTTP status and emits `gsi-team` / `gsi-update`. No public interface changed.
- `reconcile_draft` now enforces `MAX_BANS_PER_TEAM = 5`. Before this, picks were capped at 5 per side by `validate_pick`, but bans were unbounded: renumbered or stale snapshots could append a sixth ban to a side, permanently removing that hero from `available_heroes`. The property test found this (`more than 10 bans`), the guard fixed it, and `lifecycle_bans_are_capped_per_team` pins it. Five is derived from the five `banN_id` slots and the audited CM order, not from a guess about slot timing.
- The ingestion core still skips exactly one payload when a new draft is detected. This is unchanged and documented below as a residual ambiguity.

New tests (`apps/desktop/src-tauri/src/gsi/lifecycle_tests.rs`, 18 tests):

| Area | Tests | What is asserted |
| --- | --- | --- |
| Consecutive matches (A) | `lifecycle_consecutive_matches_do_not_leak_state`, `lifecycle_strategy_time_after_draft_keeps_state` | init -> hero selection -> actions -> post-game/in-game -> second hero selection. The reset payload is skipped, no match-1 hero or ban survives, the pool is restored, match-2 actions are accepted, team/turn state is rebuilt, replay is a no-op, strategy/pre-game do not reset. |

Remaining gaps / documented ambiguities:

- **No live GSI stream.** The fixtures are hand-written from the documented payload shape; no captured traffic or in-game session was replayed. A payload-shape surprise in the real client is still unverified.
- **warp + Tauri emission not covered.** The tests stop before the HTTP status and the `gsi-team` / `gsi-update` events. `apply_gsi_payload` is shared, but the handler's match arms are only type-checked.
- **Reset skips one payload.** The reset-triggering payload is deliberately not ingested because it can still contain the finished game's slots. A second stale `HERO_SELECTION` snapshot arriving after that (out-of-order delivery, which GSI does not promise against) is structurally indistinguishable from a new draft and would be accepted. No heuristic was added.
- **Undo suppression is hero-scoped for the match.** It cannot tell a stale re-add from a genuine later pick of the same hero in the same match; the latter is ignored until reset. An explicit manual pick lifts it. This is intentional and tested as the current contract.
- **Append-only by design.** Ingestion never removes an action based on a snapshot, so Dota-side corrections that are not user undos cannot be represented. In CM, actions are not reversible, so this is acceptable for now.


### P0-3. Incorrect Captain's Mode fallback sequence

- `gsi.rs:270-291` encodes 6 bans -> 6 picks -> 4 bans -> 4 picks (20 actions).
- Audited current sequence: 4 bans -> 4 picks -> 4 bans -> 4 picks -> 2 bans -> 2 picks.
- The fallback is used when GSI omits `activeteam`/`pick` (`gsi.rs:304-311`) and is the only ordering authority in that case.

Impact: silent turn/team inversion when the fallback is exercised.

Status: **confirmed** by code inspection and table comparison.

### P0-4. Expensive recommendation execution

- `ml.rs:122` serializes every inference behind a `Mutex`; `ml.rs:242` runs one inference per candidate.
- `ml.rs:447` `build_feature_map` allocates a fresh ~887-entry `HashMap` for each candidate.
- The engine scores every available hero while holding the state read guard (`engine.rs:540-611`).
- `App.tsx:79-83` and `OverlayWindow.tsx:49-52` each request recommendations per `gsi-update`, and the overlay also polls every 5 s (`OverlayWindow.tsx:68-70`).
- Analytical estimate: up to ~126 inferences + ~126 feature-map builds per request; ~252 per GSI event across both windows. **Not measured in this audit.**

Status: **confirmed structurally**; latency magnitude is an estimate pending benchmark (see ROADMAP P0-4).

## 5. P1 findings

### P1-1. No debounce, coalescing, cancellation, or stale-response protection

`App.tsx:79` fires `getDraftState` + `getRecommendations` on every event and applies responses unconditionally. GSI can emit several payloads per second. Stale responses can overwrite newer state.

Status: **confirmed**.

### P1-2. Overlay can blank out and ignores the player's side

`OverlayWindow.tsx:49-54` wraps recommendations and `predictDraftValue` in one `Promise.all`; a missing/failed model rejects both. The overlay also defaults to `radiant` and never listens to `gsi-team` (`OverlayWindow.tsx:23,61-76`).

Status: **confirmed**.

### P1-3. Overlay toggle steals focus

`Header.tsx:43` calls `setFocus()` after showing the overlay, pulling focus from Dota 2.

Status: **confirmed**.

### P1-4. User-facing settings with no runtime effect

`overlay_enabled`, `overlay_position`, `overlay_size`, `ml_enabled`, `auto_update_meta`, and `preferred_language` are editable or stored but not applied. `ml_enabled` is the most damaging: users cannot disable the weakest 25% of the score. `AppConfig` also carries dead fields, and the default model path is the stale `ml/models/draft_model.onnx` (`models.rs:579-581`).

Status: **confirmed**.

### P1-5. Feature pipeline cannot reproduce the shipped feature set

`ml/feature-engineering/processor.py`: `_load_hero_matchups` expects name-based `hero_a`/`hero_b` + `winrate`, while `process_all_pick_matches` writes numeric IDs + `hero_a_winrate`. `all_hero_ids = 1..139` is hard-coded while the manifest contains `rad_wr_hero_145`/`_155`. Lane features are commented out.

Impact: the matchup/roster feature block cannot be regenerated from current code; retraining produces a different contract than the shipped model.

Status: **confirmed** by code inspection; end-to-end regeneration not run.

#### P1-5 remediation (2026-10-28)

Status: **`fixed_unverified`** for the name set; real-data regeneration not run.

- `ml/tests/test_feature_schema.py` runs the real `FeatureProcessor.process_match` on a deterministic 26-match fixture and compares the emitted columns with the tracked schema/features pair.
- Without matchup data the processor emits exactly the **887** shipped names. All 633 non-per-hero-win-rate inputs are compared; 631 match the shipped order exactly. The two `*_ban_avg_winrate` columns are emitted beside the other win-rate aggregates while the shipped parquet lists them last (indices 885/886); their position is first-seen dataset history, so the test pins membership, not position.
- The 254 per-hero win-rate columns match as a set; the shipped order depends on which match first introduced each hero.
- With matchup data the processor emits **894** names = shipped set + 7 matchup features. The bundled processed parquet has no matchup columns, so shipping them requires a regenerated dataset, a retrain, and a new export.
- A generated row encodes to a finite 887-element vector and the bundled ONNX model accepts it.

Residual: `process_all()` gathers thread results in completion order, so a regenerated dataset's column order can vary; lane features remain disabled; the 1.9 GB dataset was not regenerated. Next: canonicalise column order/row order, then regenerate a sample and diff against the schema.

### P1-6. Post-draft and ordinal features create train/serve skew

`ml/training/train_full.py` includes `duration`, `avg_mmr`, `game_mode`, `lobby_type`, and raw `rad_pick_i`/`dire_pick_i` as numeric ordinals. `duration` is post-draft and is replaced by a median at inference.

Status: **confirmed**; impact magnitude not measured.

#### P1-6 remediation evidence (2026-10-28)

Status: **`in_progress`**. Magnitude is now measured; no feature has been removed and no model has been retrained.

- Replacing `patch`, `patch_version`, `duration`, `avg_mmr`, `game_mode`, and `lobby_type` with schema defaults (what the runtime actually does) moves the held-out test from AUC 0.5388 → **0.5122** and Brier 0.2481 → **0.2495**. The 0.0266 AUC gap is the measured train/serve skew for this artifact.
- Per-feature audit on 10,213 test rows: `duration` AUC 0.4624, gain rank 6; `game_mode` 0.5103, rank 327; `lobby_type` 0.5009, no gain; `avg_mmr` constant 0, no gain; `patch` categorical, gain rank 131; `patch_version` no gain.
- Ordinal pick slots are individually near chance (AUC 0.4947-0.5027, gain ranks 298-411).
- Split integrity: 81,694 / 10,211 / 10,213, zero `match_id` overlap, strict time boundaries. These checks are part of every gate run.

The numbers argue against a quick schema edit: removing leakage may close only ~0.03 AUC, and the model is near baseline in both modes. A candidate must be trained and evaluated end-to-end.

#### P1-6 ablation result (2026-10-28, session 4)

Status: **`in_progress`** — the ablation was run end-to-end; the candidate was rejected. Full tables live in [`ROADMAP.md`](ROADMAP.md) §3.

- Harness `ml/training/ablation.py`: fixed XGBoost config and seed, validation-only selection, then a refit at the selected round count so the exported ONNX matches the evaluated trees (parity 1.2e-07).
- Validation (10,211 rows, inference mode): baseline 887 features 0.5340 AUC / 0.2486 Brier / 0.0245 ECE; no-context 881 features **0.5358 / 0.2481 / 0.0151**; no-pick-order 877 features 0.5332 / 0.2487 / 0.0248; combined 871 features 0.5344 / 0.2481 / 0.0203. All AUC CIs overlap; the differences are not individually significant.
- The measurable win is structural: with the six context fields absent, `as_trained` and `inference` are identical (0.5358 in both), so there is nothing left for the runtime to substitute.
- Partial-draft simulation (AUC with 0/1/2/3/5 picks known per side): baseline 0.5239 → 0.5340; combined 0.5315 → 0.5344. The ordinal slots cost ~0.008 AUC at the first-pick stage, which is consistent with their schema defaults being real hero ids (66, 64).
- Single test run of the selected candidate (`quality_gate.py`, exit 1): AUC 0.5136 (0.5024-0.5248), Brier 0.2494, log loss 0.6919, accuracy 0.5255, ECE 0.0139, against a constant-prior baseline of Brier 0.2493 / log loss 0.6917 / accuracy 0.5274. Validation → test lost 0.0222 AUC, so the validation window does not represent the test window.
- Conclusion: leakage removal is necessary for an honest contract but nowhere near sufficient. **The 2026-10-28 test window has been consumed once** and cannot back another selection claim.

#### Discovery: the shipped dataset mislabels bans as picks (2026-10-28, session 4)

`processor.py` read `pb.get('is_pick', True)` while STRATZ payloads (all 4,000 sampled raw files) use camelCase `isPick`. Bans therefore satisfied the default and were registered as picks:

- 82,739 / 102,118 rows have 12 Radiant presence flags instead of 5; only 15,841 have 5.
- `rad_ban_*` is all-zero for 97,402 rows.
- The runtime builds 5 picks + ≤5 bans per side, so training and serving disagree on the *core* presence features — a larger mismatch than every ablated group combined.

Parsing is fixed with a STRATZ-shape regression test, but the dataset was not regenerated in-session; all metrics in this document still reflect the corrupted encoding. This is the first item in ROADMAP §8. It also means P1-5's "reproducible 887 names" property is intact while the underlying *values* are wrong.

### P1-7. `game_mode` is mis-encoded: Captains Mode is stored as All Pick

Discovered 2026-10-29 (session 9) while segmenting validation metrics by mode.

`processor.py:708-711` maps the STRATZ string enum with

```python
gm = match.get('game_mode') or match.get('gameMode', 0)
if isinstance(gm, str):
    gm = 22 if 'CAPTAIN' in gm.upper() else 0
```

so every STRATZ match whose mode contains "CAPTAIN" is written as **22 (All
Pick)**, and every other STRATZ mode as **0 (unknown)**. Verified against the raw
payloads for all 102,118 rows:

| True mode | Rows | Stored |
| --- | --- | --- |
| `CAPTAINS_MODE` | 87,746 | 22 |
| `CAPTAINS_DRAFT` | 3,172 | 22 |
| `ALL_PICK` | 11 | 0 |
| `ALL_PICK_RANKED` / `ALL_RANDOM` / `LEAST_PLAYED` | 133 / 86 / 23 | 0 |
| `RANDOM_DRAFT` / `SINGLE_DRAFT` / `TURBO` (STRATZ) | 3,285 / 1,422 / 606 | 0 |
| OpenDota numeric 2 / 23 / 22 | 4,475 / 918 / 241 | 2 / 23 / 22 (correct) |

Impact:

- Any analysis segmented by `game_mode` is invalid. This is how the corpus was
  misread as "89% All Pick" before this session; the real figure is **90.3%
  Captains Mode** (87,746 + 4,475).
- `CAPTAINS_MODE` (7 bans/side) and `CAPTAINS_DRAFT` (3 bans/side) are
  indistinguishable in the column.
- The 871-feature candidate drops the match-context group, so **no reported
  session-7/8 metric changes**. The bundled 887-feature model does train on the
  column, and the runtime substitutes 22.

Status: **`open`**, deliberately not patched. Fixing the mapping changes the
values of a shipped feature, which requires a regenerated (v3) dataset and a new
fingerprint; doing it silently would leave `eval_split_v2.json`'s dataset hash
pointing at different content than the code produces. The next dataset
generation should map the enum explicitly (`CAPTAINS_MODE -> 2`,
`CAPTAINS_DRAFT -> 4`-family, etc.), keep every mode's raw string in the manifest,
and treat `RANDOM_DRAFT`/`SINGLE_DRAFT` as a different population.

## 6. P2 findings

- **Security:** `tauri.conf.json:44` sets `"csp": null`; `load_ml_model` accepts an arbitrary path (`commands.rs:380`), which can sideload an `onnxruntime.dll`; `capabilities/default.json` grants `shell:default`, `fs:default`, `dialog:default` to both `main` and `overlay`; GSI auth is optional by default.
- **Semantics:** `confidence` is literally the score (`engine.rs:665`); `lane_balance` is constant `0.5` (`engine.rs:807`); `simulation.rs:196` uses immediate value as confidence; risk levels are score thresholds; no role/position, ban, or phase-aware output.
- **Crash paths:** `partial_cmp().unwrap()` on f32 keys at `engine.rs:595`, `simulation.rs:96`, `simulation.rs:139`.
- **Locking / async:** several async commands lock `std::sync::Mutex` directly (`commands.rs:63,102,115,140,160,168,178,187`); `predict_draft_value` introduces a lock-order inversion risk; `DraftSimulator` clones the whole engine including data maps (`simulation.rs`).
- **Ops:** no log rotation (`lib.rs:23-63`); `info!` on every recommendation (`commands.rs:38`) and GSI update (`gsi.rs:241`); ONNX load is synchronous on startup/IPC.
- **Data:** `ml/datasets` = 121,746 files / 1.9 GB (1 tracked); `ml/models` = 115 files / 17.7 MB (4 tracked); no incremental cache, versioning, or retention.
- **Docs:** `README.md` and `ML_TRAINING.md` were corrected on 2026-10-28 to the bundled 887-input model's measured metrics; older step/design docs still carry historical numbers. `docs/RefactorML.md` is empty.
- **Unused surface:** `getDataHealth` exists but nothing surfaces it in the UI.
