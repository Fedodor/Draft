## 1. Executive summary

The deterministic core is healthy: every local check passes, including 71 Rust
tests, 19 frontend tests and 163 Python tests. The remaining risk is no longer
mostly unit-level logic. It is the **packaged runtime contract** — what the app
does when Tauri, CSP, persisted settings, and two windows interact. That is
exactly the layer the test suite cannot see, and this pass found five defects
there. All five are fixed in this session.

The most consequential finding is the Content-Security-Policy: as shipped, it
blocked **every hero portrait** (Steam CDN) and **both web fonts** (Google
Fonts). The app type-checks, builds, and passes tests while rendering broken
imagery. This is the P2-1 risk the roadmap already listed ("CSP/capabilities are
type-checked, not launched in CI"); this audit confirms it was not theoretical.

## 3. Findings fixed in this session

### A-01 (P1) — The CSP blocked all hero portraits and web fonts

**Evidence (before the fix)**

- `tauri.conf.json` CSP: `img-src 'self' asset: … data: blob:` — no
  `https://cdn.cloudflare.steamstatic.com`.
- `src/components/HeroPortrait.tsx` builds every portrait URL as
  `https://cdn.cloudflare.steamstatic.com${hero.icon}`; `RecommendationCard.tsx`
  does the same for its background image.
- `index.html` loads `https://fonts.googleapis.com/css2?...` and the resulting
  files from `https://fonts.gstatic.com`; the CSP had no matching `style-src` or
  `font-src` origins.

**Impact:** in a packaged build, every hero portrait is blocked and the UI falls
back to three-letter placeholders; Inter/JetBrains Mono never load. Type-checks,
lint, Vitest, and `npm run build` all stay green, so nothing in the current gate
can detect it.

**Fix:** allow only the three origins the UI actually uses:

```
style-src 'self' 'unsafe-inline' https://fonts.googleapis.com
img-src   'self' asset: … https://cdn.cloudflare.steamstatic.com data: blob:
font-src  'self' data: https://fonts.gstatic.com
```

**Guard:** new `test_csp_allows_assets_the_ui_loads` in `src/lib.rs` parses
`tauri.conf.json` and asserts each origin is present in the *specific*
directive, so a future CSP tightening fails a test instead of silently breaking
the UI.

**Not verified:** actual rendering in a launched Tauri window. No GUI was
available. The test pins the policy, not the browser result.

### A-02 (P1) — Model path: allow-list bypass at startup and no runtime effect

Two defects in the same feature:

1. `lib.rs` loaded `config.ml_model_path` directly when the file existed. The
   allow-list in `commands::canonical_model_path` (app data, resource dir,
   `cwd/ml/models`, repo `ml/models`) was applied only to the `load_ml_model`
   IPC command. A persisted config could therefore point outside those roots at
   startup — the exact DLL-sideloading path P2-3 was supposed to close.
2. The Settings "Model Path" field saved the string through `set_config`, but
   nothing loaded it. `api.loadMlModel` exists and is unused by the UI. The
   setting appeared to save and had no effect until the next app start, while
   the panel kept showing the previous model status.

**Fix:**

- `canonical_model_path` is now `pub(crate)`, requires an actual file
  (`is_file()`, not a directory), and applies the same root check through a
  testable `path_is_within_roots` helper.
- Startup resolves the configured path through that function and falls back to
  the bundled resource when it is rejected or missing.
- `set_config` now detects a changed path and loads it *before* persisting. A
  failed load returns `ModelError`, so "Save" cannot claim success for a model
  that will never load. With no stored config yet, the default path is skipped
  because startup already attempted it; an explicit custom path is validated and
  loaded.
- `SettingsPanel` refreshes `getMlStatus()` after save/reset, so the panel shows
  the artifact that is actually loaded.

**Guard:** `test_model_path_must_live_under_an_allowed_root` pins the containment
rule. The `AppHandle`-dependent resolution itself is not unit-tested.

### A-03 (P1) — Disabling the overlay collapsed the main window

**Evidence:** `App.tsx` returned a full-screen "Show Overlay" button whenever
`isOverlayVisible` was false. That flag is persisted in `ui-store`, and
`Header`'s geometry effect sets it to false whenever `config.overlay_enabled` is
false. The result: after turning the overlay off, the dashboard (including
Settings) is replaced by a button; showing it again remounts `Header`, whose
effect immediately hides the overlay and sets the flag false again.

**Impact:** a user who disables the overlay cannot reach Settings to re-enable
it. The main window and the overlay window are separate concepts, but they
shared one visibility flag.

**Fix:** removed the early return and the now-unused store fields from `App`.
The dashboard always renders in the main window; only the separate overlay
window is shown/hidden.

### A-04 (P2) — Manual draft summary ignored the selected side

`HeroPicker` labelled the Radiant list "ALLY PICKS" and the Dire list "ENEMY
PICKS" regardless of `selectedTeam`. On Dire, the counters were reversed.
The panel now derives `allyPicks` / `enemyPicks` from `selectedTeam`, matching
`DraftOverlay` and the recommendation request.

### A-05 (P3) — Non-finite overlay geometry could be persisted

The settings inputs use `parseInt('')`, which produces `NaN`. `validateConfig`
and `AppConfig::validate` checked the port, token, and model path only, so NaN
(or a 40 px) position/size could be saved. `Header` then calls
`LogicalPosition`/`LogicalSize` with it and swallows the failure.

**Fix:** both validators now reject non-finite coordinates and sizes below
100×100. `AppConfig` has a new regression test; the frontend uses the same
rules before calling `set_config`.

not see them until the index is committed and pushed.

### A-07 (P2) — Python dependencies are not reproducible

`ml/requirements.txt` uses lower bounds only (`pandas>=2.1.0`, `numpy>=1.24.0`,
`xgboost>=2.0.0`, …) with no lockfile or hashes. CI installs on Python 3.11 while
the verified environment is 3.10.11. A fresh resolve can pick a different
NumPy/pandas/XGBoost generation than the one the golden fixture and quality gate
were validated against.

**Action:** produce a pinned lock (`pip-compile` or `pip freeze` for the
verified interpreter), install from it in CI, and align the CI Python version
with the verified one (or verify both).

### A-08 (P2) — Unused Tauri plugins and broad capabilities

- `@tauri-apps/plugin-dialog`, `plugin-fs`, `plugin-opener`, `plugin-shell`,
  `plugin-store` are dependencies but have **no import** anywhere in
  `apps/desktop/src`.
- `tauri-plugin-updater` is in `Cargo.toml` but is never initialized in
  `lib.rs` and has no capability entry.
- `capabilities/default.json` grants `shell:default`, `fs:default`,
  `dialog:default`, `store:default`, and `opener:default` to the main window.

**Impact:** dead weight plus a wider IPC surface than the UI uses. Low direct
risk for a local desktop app, but it contradicts the least-privilege work that
created `overlay.json`.

**Action:** remove the unused plugin registrations, permissions, and packages in
one change, then re-run a packaged launch before merging. Not done here because
it needs a runtime/package check this environment cannot provide.

### A-09 (P2) — Explanations name heroes by numeric id

`MatchupScorer::explain` emits `"Strong vs 12 (55% winrate)"` and
`SynergyScorer::explain` emits `"Synergizes with 44 …"`. `RecommendationCard`
displays those strings verbatim. The numeric ids are meaningless to a player,
and explainability is a stated product requirement.

**Action:** give both scorers a `HashMap<HeroId, String>` built from `hero_db`
(fallback to the id for unknown heroes) and assert the rendered text in the
existing scorer tests. Small, isolated change; not bundled here to keep this
audit's diff reviewable.

### A-10 (P3) — Runtime paths are still unverified

The GUI, CSP in a real webview, Tauri window APIs, warp status/event emission,
and a live GSI stream remain untested at runtime. A-01 and A-03 are direct
evidence that this gap is productive for bugs. This audit does not close it; it
narrows what needs to be checked.

**Action:** build and launch the packaged app, confirm portraits/fonts and
overlay show/hide/drag, then replay a captured multi-match GSI stream. This
matches ROADMAP §8 task 2.
