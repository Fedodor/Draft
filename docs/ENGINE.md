# Draft Engine & Scoring System

The `DraftEngine` is the heart of the Smart Draft Assistant, implemented in Rust for maximum performance and reliability.

## DraftEngine Structure

The `DraftEngine` maintains an internal `DraftState` and uses a `DraftScorer` to evaluate possible hero picks. Hero data is loaded from the SQLite database at startup.

```rust
pub struct DraftEngine {
    pub state: Arc<RwLock<DraftState>>,
    pub hero_db: Vec<Hero>,
    pub scorer: DraftScorer,
}
```

### Hero Data Source

The engine reads hero data from the SQLite database (`smart_draft.db`), which is populated by the `seed_heroes` binary from `infrastructure/seeders/`. The database contains:

- **126 heroes** with full base stats (strength, agility, intelligence, gains, armor, attack range, move speed, etc.)
- **Hero attributes**: `PrimaryAttribute::Str`, `Agi`, `Int`, and `All` (Universal heroes)
- **Attack types**: `AttackType::Melee` and `AttackType::Ranged`
- **Hero semantics**: initiation, stun, save, push, scaling, mobility, durability, teamfight, splitpush, vision, magic/physical/pure damage, disable count, lane strength (early/mid/late), tempo profile, and role probabilities

## Modular Scoring System

The engine uses a trait-based scoring system, allowing for easy expansion and testing. Any struct implementing the `Scorer` trait can be added to the recommendation pipeline.

### The Scorer Trait

Every scorer is **team-aware**: the `team` parameter tells the scorer which side is being evaluated, so allies/enemies are selected correctly for both Radiant and Dire.

```rust
pub trait Scorer {
    fn score(&self, hero: &Hero, state: &DraftState, team: TeamSide) -> f32;
    fn explain(&self, hero: &Hero, state: &DraftState, team: TeamSide) -> Vec<String>;
}
```

All scorers return values in `[0.0, 1.0]` with `0.5` as neutral, so components combine cleanly.

### Current Scorers

1.  **MatchupScorer**: Evaluates how well a hero performs against the enemy's current picks (advantage normalized from `[-1, 1]` to `[0, 1]`).
2.  **SynergyScorer**: Evaluates how well a hero synergizes with the ally's current picks (signed synergy mapped to `[0, 1]`).
3.  **CompositionScorer**: Evaluates if a hero fills a missing role in the team, using real ally role data from the hero database.
4.  **MLScorer**: Runs the bundled ONNX model (XGBoost, 887 features) on the simulated post-pick draft state; outputs the picking team's win probability.

At startup, `DraftEngine::initialize` first resolves the persisted active patch from the `app_settings` table, then loads `hero_matchups`, `hero_synergies`, and `meta` for that patch and passes both maps to `DraftScorer::set_data`, so the matchup and synergy scorers are backed by the same data as the UI. When no patch is persisted, matchup/synergy/meta lookups are skipped and a warning is logged. Hero roles are canonicalized to lowercase at the scorer boundary (`"Pusher"` -> `"push"`), and `PrimaryAttribute::All` is preserved on database reads and writes. Real seed data is generated by `ml/training/export_scoring_seed.py`; `seed_matchups --synthetic` writes patch `synthetic` rows and is the explicit development-only fallback. `DraftEngine::data_health()` (Tauri `get_data_health`) reports schema version, row counts, active patch, and WAL status for startup diagnostics. See [`STEP_05_DATA.md`](STEP_05_DATA.md).

`DraftEngine::score_breakdown(hero_id, team)` returns the matchup, synergy, composition, meta, comfort, ML, and total scores for a candidate. It is exposed through the `get_score_breakdown` Tauri command.

Manual drafting goes through `validate_pick`/`validate_ban` before mutation. Turn state is not enforced, so users can correct either side; each action is pushed to a `DraftAction` undo stack and reversed by `undo_last_action`. See [`STEP_04_IPC.md`](STEP_04_IPC.md).

## Recommendation Logic

When `get_recommendations(team, limit)` is called:
1.  The engine iterates through all available (unpicked/unbanned) heroes.
2.  Each scorer is evaluated for the requesting team, then combined as a **weighted average** (weights in `scorer.rs`, summing to 1.0):

    | Component    | Weight |
    |--------------|--------|
    | Matchup      | 0.25   |
    | Synergy      | 0.20   |
    | Composition  | 0.15   |
    | ML           | 0.25   |
    | Meta         | 0.10   |
    | Comfort      | 0.05   |

3.  Because weights sum to 1.0 and inputs are bounded, the total stays in `[0, 1]` without saturating the clamp — scores remain discriminative.
4.  The top N heroes are categorized (top/safe/aggressive/comfort/anti-meta) and returned with explanations.

## Database Operations

The `database` module (public, in `src/database.rs`) provides:

- `Database::new(data_dir)` — Creates/opens the SQLite database and runs migrations.
- `upsert_hero(&self, hero: &Hero)` — Inserts or updates a hero record.
- `get_all_heroes(&self) -> Vec<Hero>` — Returns all heroes from the database.
- `get_hero(&self, hero_id: HeroId) -> Option<Hero>` — Returns a single hero by ID.
- `upsert_hero_semantics(&self, sem: &HeroSemantics)` — Inserts or updates hero semantic attributes.
- `get_all_hero_semantics(&self) -> HashMap<HeroId, HeroSemantics>` — Returns all hero semantics.

## Machine Learning Integration

The `MLScorer` loads a bundled ONNX model (`draft_model_xgboost_full.onnx`, XGBoost TreeEnsembleClassifier, 887 features) via the `ort` crate at startup. For each candidate it simulates the pick, builds the full feature vector (`build_feature_map`), and runs inference. The model outputs a Radiant win probability, which is flipped for Dire picks. When the model is unavailable, the scorer returns the neutral `0.5`.

> [!IMPORTANT]
> The system is designed to function perfectly even if the ML layer is disabled, ensuring explainability and reliability at all times.
